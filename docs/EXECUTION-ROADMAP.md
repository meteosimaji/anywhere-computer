# 独立した実行基盤の実装記録

2026-09-12: 添付の5段階すべてを継続実装する依頼。Python engine と既存の
未コミット監査修正を維持し、Codex互換はGUIの必須条件にしない。
以下は受け入れ管理であり、チェックのない項目を完成扱いしない。

製品方針（2026-09-12、ユーザーの最新指定）: 操作の許可はChat側の設定に従う。
Anywhere Computer独自の作業範囲承認画面や操作ごとの確認は設けない。
接続認証とOSが必要とする権限設定は初期セットアップにまとめ、設定の簡単さと
Codexでできる作業を通常Chatから実行できることを優先する。外部サービスが
要求する追加入力は同じ操作へ返せるようにするが、独自の承認を重ねない。

更新方針（監査後のユーザー指定）: 初回設定後、stableの検証済み配布物を
待機中に自動適用する。実作業中は待ち、適用ごとの独自確認は設けない。
ChatとCodexは共通エンジンを使用する。まず単一エンジンのidle更新を通し、
長時間セッションを保持する複数ワーカーへの拡張は後段で扱う。
監査A1–A4とCIを先に修正し、版情報の一元化、GitHub取得、共通エンジン切替、
両クライアントの受け入れ、独立GUIの配布統合の順で進める。

監査後の進捗（alpha 3を公開・常駐版へ適用。詳細は
[更新検証記録](UPDATE-VERIFICATION-2026-09-12.md)）:

- 台帳移行を明示トランザクションに変更し、途中失敗のロールバックと
  部分移行済み台帳の修復を試験。スキーマ互換範囲の読取専用検査を追加。
- 遅れて完了したPlugin画像を`operations_get`でもMCP画像として返し、
  状態取得自身を更新待ちの実作業数から除外。
- 配布版情報をPython版から生成し、commit・未コミット状態・API/台帳互換範囲と
  配布物ハッシュを`bundled/release.json`へ記録。現段階の検証表示は`unverified`。
- 停止直前に接続し、停止受付後に読み終えた要求が実行される競合を再現・修正。
  停止中は実行せず、再接続後に同じ操作IDで再試行する応答を返す。
- HTTPは現在も専用Engineを所有し、stdio用の常駐Engineとは別。
  共通化時にはHTTP認可ごとの操作ID変換・履歴照会制限を維持する必要がある。

GitHubからのstable取得・検証・自動切替は未実装。
共通Engineへの接続と移行は以下のとおり隔離試験まで進めている。
実環境での共通化後のChat/Codex両入口の受け入れは未確認。

alpha 3公開後のローカル変更: エンジン状態に`engine_api_version`を追加し、
通常のMCP接続はコードのハッシュが異なっても互換APIの既存エンジンを再利用する。
APIが不明・非互換の場合は停止・置換せずに接続エラーを返す。
版を置き換える処理は明示的な`anywhere start`に限定する。
実ローカル通信の試験で、異なるクライアント版の接続後もinstance IDと
保存済み操作結果を維持することを確認。既に実行中のalpha 1–3の旧コードを
後から変更するものではなく、この変更の常駐版への適用はまだ行っていない。

共通エンジンへのHTTP接続経路をローカル実装した。`http_service`の
`agent_directory`指定で、別Engineを生成せず既存の認証済みローカル通信へ接続する。
公開MCPカタログに出さない内部経路で検証済み認可を転送し、既存のRemoteAgentが
操作IDの分離・ツール制限・履歴照会制限を適用する。実HTTP試験ではローカルと
同じinstance ID、認可の分離・失効、HTTP入口再起動後の同一操作IDの重複防止を確認。
内部経路もローカル資格情報を要求する。HTTP入口の終了では共通Engineを終了しない。
移行前の設定は従来の配置を維持する。実環境の共通化やstable自動更新の完成を
意味しない。

保存先の共通化準備: `state_migration.stage_shared_engine`は両サービス停止中に
台帳・upload/downloadのSQLiteスナップショットとハッシュ付きバックアップを
新しい保存先へまとめる。元の保存先・資格情報・接続先は変更しない。
同一IDの異なる記録、明示設定の不一致、未知のテーブル、結果/バックアップの
ハッシュ不一致は移行を拒否し、不完全な移行先を公開しない。
旧5列台帳のコピー上での移行、移行後の結果回収・重複防止・復元・保存済み
download読み出し・途中uploadの完了を隔離試験で確認した。
この準備処理を下記の管理コマンドへ接続した。実環境には未適用。

保存先選択の起動対応: `engine-selection.json`でエンジンのデータ保存先だけを
選び、`agent.json`とローカル資格情報の参照先は従来の制御ディレクトリに保持する。
切替途中を示すマーカー、無効な選択、失われた移行先台帳があれば起動を拒否し、
古い保存先への暗黙の復帰や空台帳の再作成はしない。
HTTP設定の`shared_agent_directory`も起動時に読み込み、共通入口へ接続する。
保存先を選んだ実ローカル通信で既存操作の回収、保存したHTTP設定からの
再起動・認証維持・重複防止を確認した。実環境の設定は変更していない。

`engine-unify --state-dir <local-control> --http-state-dir <http-control>`で、
両サービス停止中の移行と両設定の切替を一括実行する。切替記録が残る場合は
同じコマンドで続行する。各設定の書き込み後や完了応答前の中断から、既存認証と
操作IDを維持して再接続する試験を追加した。準備後に元データや移行先が変更された
場合は、古いスナップショットを適用せず停止する。これは実行前確認画面ではない。
旧バイナリはこの切替記録を認識しないため、最初の共通化前に両入口を対応版へ
更新して旧プロセスを終了する必要がある。旧バイナリへの復帰はサポートしない。
転送管理コマンドも選択先を読み、共通化後は`storage_scope=shared`を返す。
CLIによるOSサービスの停止・再起動の一括管理と実環境受け入れは未実施。
