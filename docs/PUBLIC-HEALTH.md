# 公開経路の任意監視（開発中）

`anywhere remote-health-enable --state-dir PATH` は現在の HTTP resource を監視対象として保存する。
このコマンドはサービスを開始せず、OS の自動起動も登録しない。
起動中の `remote-serve` は設定を読み、ローカルと公開 HTTPS のメタデータを確認する。
既定では無効であり、未設定時には監視のための外部通信も履歴作成もしない。

確認後の待機は30秒、確認処理自体の上限は10秒。認証情報を送らず、
既存のメタデータ診断を使う。成功は metadata の到達を示すだけで、認証済みツール実行の成功は保証しない。
最新の時刻・到達状態・連続失敗数を保存し、`remote-doctor` に過去の観測として表示する。
この観測だけを理由にサービスや接続子を再起動しない。

`anywhere remote-health-disable --state-dir PATH` で無効化する。
すでに開始した確認は最大10秒の範囲で終了する場合があるが、無効化後に結果を保存しない。
保存済みの最新観測は残り、現在の疎通の証明には使わない。
HTTP resource を変更すると新しい宛先は自動的に監視せず、再度 enable が必要になる。
監視開始時だけでなく、公開通信直前にも承認済み resource と診断側が読んだ設定を照合する。
設定変更と確認処理が重なっても、変更後の宛先への通信を始めない。
サービス終了時は進行中の監視処理をキャンセルする。

設定変更ごとに世代識別子を更新し、無効化後に同じ宛先を再有効化しても、以前の世代で
開始した結果を保存しない。従来の世代なし設定は空の識別子として読み込み、次回変更時に
識別子を付ける。新しい世代では連続失敗数もリセットする。

`tests/test_remote_health.py` で未設定/無効/宛先変更時の無通信、正常→障害→回復、
実行中の無効化、キャンセル伝播、破損履歴の非開示を検証する。
この試験の外部宛先診断は差し替えているため、実ネットワークの障害復帰を証明しない。
関連41テストは2026-09-09に成功。実ローカル HTTP サービスを使い、公開側の診断だけを
差し替えた障害→回復と、履歴保存失敗後も確認を継続する試験を含む。
公開先設定の不一致時に公開通信しないことも、実ローカル応答と組み合わせて確認した。
配布用 wheel を更新し、全体 pytest は416件成功・5件スキップ（39.02秒）。
プラグイン構造検証、Ruff、通常/Windows対象の型検査も成功した。
追加の実ネットワーク障害試験と、この変更の三 OS CI は未完了。
ユーザー環境での監視有効化・本番常駐登録は行っていない。
