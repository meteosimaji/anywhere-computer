# バイナリファイルの分割転送

`files_read_binary` と `files_write_binary` は画像・圧縮ファイルなどのバイト列を
base64 で受け渡します。通常の MCP 接続と同じ経路を使い、実行時ライブラリを追加しません。
読み取りは1ファイル1 GiBまで、単純書き込みは16 MiBまで、1回の読み書きは256 KiBまでです。
読み取りは256 KiBずつ全体を走査して SHA-256 を計算し、要求した範囲だけをメモリに保持します。
各リクエストで全体を再走査するため、大きいファイルでは時間とディスク I/O が増えます。
読み取り中のサイズ・更新時刻の変化は拒否しますが、OS の不変スナップショットではありません。

## ダウンロード

最初に `files_read_binary` へ絶対パスを渡します。結果には `data_base64`、全体の
`sha256`、`chunk_sha256`、`total_bytes`、`next_offset`、`eof` が含まれます。
続きを読むときは `offset` に前回の `next_offset`、`expected_sha256` に最初の全体ハッシュを
渡します。変更を検知したら失敗し、その応答にはデータを含めません。
各チャンクのハッシュと、結合した全体のハッシュを接続元でも照合してください。

中断後も同じハッシュと保存済みオフセットで再開できます。ファイルサイズと同じ
オフセットは空データと EOF を返し、サイズを超えるオフセットはエラーです。
空ファイルにも対応します。各回でファイル全体を分割走査してハッシュを求めます。
メモリはファイル全体を保持しませんが、連続取得時の再走査コストがあります。
外部アプリが同じファイルを直接変更する間の完全なスナップショットを保証しません。

## アップロード

1. 未使用の一時ファイルの絶対パスへ `files_write_binary` の `mode: create` で最初の
   チャンクを送ります。`data_base64` は標準の正規 base64 を使い、改行を含めません。
2. 続くチャンクは `mode: append` と、前回の結果にある全体 `sha256` を
   `expected_sha256` に指定します。結果の `bytes` が確定済みの長さです。
3. 送信が終わったら、全体のバイト数と SHA-256 を元ファイルと照合します。
4. `files_move` で未使用の最終パスへ公開します。同じファイルシステム内の移動に対応し、
   既存の最終ファイルは上書きしません。

各チャンクは競合検知とバックアップ付きで確定します。複数チャンク全体を一つの
トランザクションとして扱うものではなく、一時ファイルには途中の内容が見えます。
各 append は既存の全体を読み直し、更新前の全体バックアップを保持するため、
転送サイズ以上のディスク容量と I/O を使います。バックアップの自動整理は未実装です。
0バイトの作成・置換も可能です。`mode: replace` も既存ファイルの現在ハッシュを要求します。

応答を失った場合は操作 ID を保持して `operations_get` で結果を確認します。
記録が `unknown` なら一時ファイルを `files_read_binary` で確認し、手元で計算した
確定済みプレフィックスの長さ・ハッシュと照合してください。応答がないことだけを根拠に
append を再送しないでください。同じ古いハッシュを使った新しい操作は競合として拒否します。
外部変更などでどのプレフィックスとも一致しない場合は、そのファイルへの追記を止めます。

公開時の `files_move` は hard-link と元パスの unlink を使います。途中で失敗すると
両方のパスが残る場合があります。結果不明の移動も自動で繰り返さず、両パスと内容を
確認してください。既存の最終パスを置換する専用の確定処理と自動再開 UI は今後の実装です。
専用転送 ID によるアップロードは [永続アップロード](UPLOADS.md) の経路を使ってください。

## 権限と復元

リモートでは `files_read_binary` と `files_write_binary` をそれぞれ明示的に許可します。
既存の `files_read` / `files_write` の認可だけでは、新しいツールは実行できません。
`files_restore` はテキストとバイナリ両方のバックアップを復元できるようになりました。
このツールの既存の認可もバイナリ復元に適用されます。

回帰テストでは分割読み取り、変更検知、同時追記、エージェント再起動後の操作照会・重複抑制、
バイナリ復元、TLS を通る256 KiB転送、HTTP の未認可ツール拒否を確認します。
これは別の実機や常設インターネット経路での大容量転送の検証ではありません。

## 1 GiB のローカル実測

`scripts/verify_large_reads.py --receipt <保存先>` は使い捨てディレクトリに
実際に1 GiBを書き込み、先頭・中央・末尾の256 KiBを取得して内容とハッシュを確認します。
`--mib` で1〜1024 MiBに変更できます。終了後に生成ファイルを削除し、結果には
実装識別子・測定スクリプトのハッシュ・削除確認を残します。

[2026-09-09の測定記録](research/2026-09-09-large-read-verification.json) では、
macOSのローカルFiles APIで3回とも成功し、各回約0.39〜0.40秒でした。
読み取り呼び出し中のPython追跡割り当てピークは約1.2 MiBです。
RSSは呼び出し前後の値であり、プロセス全体の最大値ではありません。
OSのファイルキャッシュを排除した測定でも、ネットワーク越しの全量転送でもありません。

1 GiB全体を256 KiBずつ取得すると4096回の走査で合計4 TiBを読み直します。
これは仕様からの計算であり、全4096回を測定した結果ではありません。
転送ごとの不変データと直接範囲取得による効率化は未実装です。
