# 永続転送 ID によるアップロード

新規ファイルへの転送に `upload_begin` / `upload_chunk` / `upload_status` /
`upload_commit` / `upload_abort` / `upload_resolve` を使えます。
1ファイルの宣言上限は1 GiB、1チャンク256 KiB、受信中・結果不明の転送は8件まで、
予約総量は4 GiBまでです。予約は物理ディスク使用量の上限ではありません。
公開時の一時ファイル、SQLiteのWAL・空きページのため追加の空き容量が必要です。

## 通常の転送と再開

1. 接続元で未使用の32桁hex `transfer_id` を作り、最後まで保持します。
2. `upload_begin` に ID、未使用の保存先 `path`、`total_bytes`、全体の `sha256` を渡します。
   親ディレクトリは先に作成してください。同じ ID と同じ条件の再送は状態照会と同じ結果に
   なり、違う条件への使い回しは拒否します。
3. `upload_chunk` に ID、確定済みのバイト位置 `offset`、正規base64の `data_base64` を
   渡します。連続したチャンクを受け付け、同じオフセット・同じバイト列の再送は重複保存
   しません。別内容や途中位置への上書きは拒否します。
4. 中断・再起動後は `upload_status` の `received_bytes` から続けます。
   `sha256` は宣言された最終ハッシュであり、未完成のプレフィックスのハッシュではありません。
5. 全チャンクが届いたら `upload_commit` を実行します。DBから順に読み、長さとハッシュを
   照合してから、一時ファイルを保存先へ公開します。既存の保存先は上書きしません。

データは `uploads/uploads.sqlite3` に残り、最終パスに途中の内容を公開しません。
全体をメモリに連結せずに処理し、各チャンク確定時にも全体バックアップを繰り返しません。
大文字小文字やUnicode表現の違いによる二重予約を避けるため、全OS共通でNFC正規化と
casefold後のパスを比較します。大文字小文字を区別するファイルシステムでも、
この比較で一致する転送は同時に予約できません。

## 公開結果が不明な場合

公開直前の意図を永続化します。その後プロセスが停止した場合、転送状態は `unknown` と
なり、自動再公開しません。通常の操作 ID の `operations_get` に加え、転送 ID の
`upload_status` を確認します。ツール応答全体が `completed` でも、`data.state` が転送状態です。

- `upload_resolve` の `action: confirm_published` は、保存先が通常ファイルで長さと
  SHA-256が一致する場合だけ、再公開せず完了を確定します。
- `action: discard_staging` はDBチャンクと予約だけを解放し、状態を `discarded` にします。
  保存先やファイルシステム上の一時ファイルは削除せず、公開できていたとも断定しません。
- `upload_abort` は受信中の転送だけを中止します。公開済み・結果不明には適用しません。

`publication_verified` は過去の完了確認を表し、その後の外部変更を否定するものではありません。
`staging_path` は記録上の一時ファイルの場所、`staging_exists` は照会時にその場所が存在するか
です。処理終了時に削除を試みますが、クラッシュや削除失敗で残る場合は場所を確認して
手動で片付けます。公開準備中に停止して `receiving` のまま一時ファイルが残った場合も、
追跡できなくしないよう新しい一時ファイルで上書きせず、既存ファイルの確認・片付けを要求します。

DBチャンクの削除はSQLite内の領域を再利用可能にしますが、DBファイルの縮小や安全消去では
ありません。終了履歴・ロックファイルの自動整理は未実装です。

## 認可と検証の範囲

HTTPでは転送 ID を認可grantごと、相互TLSでは登録peerごとに分離します。
通常のトークン更新は同じgrantを維持するため再開できますが、失効・新規ログインで
grantが変わると以前の転送にはアクセスできません。所有者向けの旧grant転送管理画面は
未実装で、必要な場合はローカル状態の管理が必要です。各uploadツールは明示的な許可を要求します。

自動テストでは17 MiBの転送、DB再オープンからの再開、HTTPチャンク応答の喪失、
一時ファイル準備中・公開直前・直後の実プロセス強制終了と照合による解決を検証します。
1 GiB全量の実機性能、大容量ダウンロード、別端末間の長時間運用はまだ検証していません。
既存ファイルを置換する大容量の確定処理、自動再開 UI、常設インターネット経路も今後の作業です。
